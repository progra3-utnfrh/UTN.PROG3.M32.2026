Para entender el flujo de App.js sin perderse, hay que tener en cuenta una regla de oro 
en React Native: el código no se ejecuta una sola vez de arriba hacia abajo como en un script clásico,
sino que da "dos vueltas" (dos renderizados).   
La 1ª vuelta (Montaje): Ocurre en el milisegundo cero cuando abrís la app. Como todavía no fueron 
a buscar los datos a MySQL, dibuja la ruedita girando (ActivityIndicator).
La 2ª vuelta (Re-render): Ocurre unos milisegundos después, cuando llega el JSON 
desde el servidor y setProductos() junto con setCargando(false) obligan a la función App() a 
ejecutarse de nuevo, pero ahora con los datos cargados.

Los 3 "momentos clave" que muestra este diagrama:
Por qué se declaran las funciones arriba pero se ejecutan después 
(Paso 2):
Cuando el intérprete de JavaScript lee const consultarProductos = () => { ... } y 
const renderProducto = ({ item }) => { ... }, no entra a ejecutar lo que tienen adentro;
solamente las "memoriza". 
El puente entre la Fase 1 y la Fase 2 (useEffect en el Paso 4):
React primero cumple con dibujar el return inicial (la ruedita girando) y, recién cuando la pantalla
ya está visible en el teléfono, dispara el useEffect que llama a consultarProductos().
El disparo de renderProducto recién al final de la Fase 3 (Paso 8):
En la primera vuelta (cargando === true), <FlatList> ni siquiera existe en la pantalla, por lo que
renderProducto no se llama ni una sola vez. Recién en la segunda vuelta, cuando cargando pasa a false, 
el operador ternario entra por el último :, monta <FlatList> y esta llama 6 veces seguidas a renderProducto.
